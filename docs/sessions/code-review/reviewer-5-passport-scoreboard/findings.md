# Adversarial Review — Passport + Scoreboard

Date: 2026-07-10
Reviewer: reviewer-5-passport-scoreboard

## CRITICAL

1. **app/agent/[id]/passport/page.tsx:253,263 — Evidence links use domain `attack.id`, not event-store event IDs.**

   The passport renders `claim.attackId` as both the visible text and the `?event=` query parameter:
   ```tsx
   href={`/battle/${battle.id}/replay?event=${claim.attackId}`}
   ```
   However, `attack.id` (e.g. `"attack_viral_to_safe_generic"`) is the domain object ID from `createDemoAttacks()` in `arena/engine/fixtures.ts:230`. The replay page's `BattleReplayClient` loads events via `/api/battles/[id]/events`, which returns events stored in `InMemoryBattleEventStore` where IDs are generated by `runtime.nextId("event")` (see `arena/engine/demo-battle.ts:55`) — producing completely different string IDs like `"evt_abc123"`.

   Worse: `BattleReplayClient` at `components/battle-replay-client.tsx:40-76` never calls `useSearchParams()` and never opens the drawer on initial load. The `selectedEventId` state is only set by `handleSelect()` from a row click. So every evidence link on the passport navigates to `/battle/{id}/replay?event=attack_viral_to_safe_generic`, but the replay page just renders the timeline with no drawer open and no auto-scroll to the matching event. The links are decorative dead-ends.

2. **app/agent/[id]/passport/page.tsx:250-253 — `passport.acceptedClaims` and `passport.rejectedClaims` store domain `attackId` field, not event IDs.**

   The `AgentPassport` type declares `attackId: string` on each claim, and `loadFromDemoBundle` pulls directly from `bundle.passport.acceptedClaims` (line 122-123). These come from the Zod-validated engine output — the field is domain-level `Attack.id`, not `BattleEvent.id`. The passport page treats them as clickable evidence links to the replay, which is the wrong ID space.

## HIGH

1. **app/battle/[id]/result/page.tsx:54 — Champion `evidenceEventId` defaults to the string `"unknown"`, not a valid event ID.**

   ```ts
   const championEvidenceId = winnerScore?.evidenceEventId ?? "unknown";
   ```
   The `findScoreEvidenceEventId` in `lib/api-client.ts:204` returns `unknown-${teamId}` when no `score_created` event is found, but the `ChampionCard` fallback is hardcoded to just `"unknown"`. This will display the literal text "unknown" in the champion card if the lookup fails — violating the invariant that evidence must be a real event ID. Even if the lookup succeeds, `championEvidenceId` is rendered as a `<code>` element with `title="Champion selection event"` but it is not a link — it is not clickable.

2. **app/battle/[id]/result/page.tsx:134-153 — Score-cell `evidenceEventId` is never clickable; the EventDrawer is never opened from the result page.**

   The local `Scoreboard` function renders score cells with `tabIndex={0}`, `title` and `aria-label` attributes, plus a tooltip span, but there is no `onClick` handler and no connection to `EventDrawer`. The tooltip shows text on hover/focus but clicking does nothing. The PRD requires every score to bind to ≥1 evidenceEventId and that the evidence must be clickable.

3. **app/agent/[id]/passport/page.tsx:158 — Champion detection logic compares `id` vs `id.replace(/-/g, "_")`, but the fallback string `"unknown"` in the result page never appears in this comparison.**

   The passport uses `const isChampion = battle.winnerTeamId === id || battle.winnerTeamId === id.replace(/-/g, "_")` to decide whether to show the gold seal ring. This is correct in isolation, but `battle.winnerTeamId` is sourced from `bundle.winnerTeamId` (engine format `viral_designer`) whereas `id` (the route param) is in UI format (`viral-designer`). The `||` clause handles it correctly here, but the same conversion is duplicated in `loadFromDemoBundle` at line 104 (`engineTeamId`) and again at 158. If `winnerTeamId` is missing from the API response, the champion badge silently misfires — and there's no `[class*="rounded-r-md"]` / `border` rule exception for it in print.css either.

## MEDIUM

1. **app/print.css:279-283 — CSS `a[href]::after { content: " (" attr(href) ")"; }` appends full URLs after every link in print, producing noisy output.**

   This rule is intended to satisfy "evidence links become plain URLs visible only in print", but it applies globally to ALL `<a>` elements — including the "View Replay" link, "Export .md" link, and any internal anchors. The print output will render something like `View Replay ( /battle/battle-42/replay )` next to each link, making the print layout noisy. A scoped selector targeting `.evidence-link` or a `.print-only .evidence-urls-print li` would be less invasive.

2. **app/agent/[id]/passport/page.tsx:311-320 — Print-only evidence URLs duplicate the `print-only.evidence-urls-print` content but the replay page never reads the `?event=` param, so the printed URL is also non-functional.**

   The `print-only` div renders human-readable evidence URLs at the bottom of the Actions section. These look correct on paper, but they link to `/battle/{id}/replay?event={claim.attackId}` — the same broken target as the on-screen links. Printing an evidence URL that can't be navigated is only slightly better than no URL.

3. **app/agent/[id]/passport/page.tsx:168-173 — Weaknesses fallback message violates the spirit of PRD §12.3.**

   The PRD invariant says weaknesses must be non-empty, but the fallback string `"Low-severity weaknesses detected — no critical gaps found."` asserts an empirical claim ("no critical gaps found") rather than acknowledging that the engine could not generate weaknesses. This may be misleading on passports when the underlying battle had genuinely unanalyzed claims. The comment on line 21 says "the passport generator guarantees this" — but this fallback is a client-side string, not a guarantee from the generator.

4. **app/battle/[id]/result/page.tsx:101 — `rankLabels` map omits "2nd" key correctly but uses `??` fallback producing "4th", "5th" etc. without ordinal awareness.**

   ```ts
   const rankLabel = rankLabels[rank] ?? `${rank}th`;
   ```
   For rank 11, 12, 13, etc. this produces "11th", "12th", "13th" (correct for English but not "11rd"). More importantly, the `aria-label={rankLabel}` on a number that says "1" or "2" or "3" reads as "1st", "2nd", "3rd" to screen readers — fine. But the visual rank-cell just displays the digit `{rank}` (line 126) with no ordinal indicator. This is by design but the note about "reversed a11y per design.md" is unverifiable since the reviewer doesn't have design spec access — and for rank >3 the ordinal text will say `${rank}th` which is a visual-only prop here, but screen readers will read it.

5. **app/battle/[id]/result/page.tsx:194-223 — `useEffect` deps on `params` Promise, not `battleId`, causing extra fetch cycles.**

   The effect depends on `params` (a Promise) not on `battleId`, so when `battleId` state is set in `params.then(...)` (line 196-197), the effect doesn't re-trigger — but the `setBattleId` call happens inside a `.then`, and subsequent renders see battleId change. In practice the effect captures the stale `params` reference only on mount, so it works — but it's fragile if Next.js ever re-creates the params promise on re-render.

6. **app/globals.css:1640-1643 — `.score-cell:focus-visible .score-tooltip` rule depends on `.score-cell` being keyboard-focusable, which the JSX does set with `tabIndex={0}` — correct — but the `.score-cell:focus-visible` selector won't match browsers that fire only `:focus` on `:hover`-triggered focus without explicit keyboard interaction.**

   This is technically working in current browsers, but the combination of `tabIndex={0}` on a `<span>` (line 139) means that when the cell receives click focus (e.g., via programmatic focus), some browsers may show the tooltip because of `:focus`, but the `display: none` → `display: block` only fires on `:focus-visible` (keyboard) and `:hover`. On touch devices, tapping a score cell will NOT show the tooltip. There is no `:active` or `ontap` handler. This is a visual + a11y gap.

### Key findings to address

The **most important issue** is the mismatch between domain IDs and event-store IDs across the entire passport evidence-link chain. The passport page claims evidence links open the event drawer for a specific battle event, but:

1. The IDs used are domain `Attack.id` strings ("attack_viral_to_safe_generic") rather than the events those attacks generated (e.g. "evt_xx99").
2. The replay page does not read `searchParams`, so the `?event=` param is ignored even if the IDs matched.

These two issues together make **every evidence link on the passport non-functional** — both on-screen and in the print export.
