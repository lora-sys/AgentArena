# R25 Frontend Components

Date: 2026-07-10

## CRITICAL

1. **components/battle-replay-client.tsx:86-93** — `useSearchParams` is called in a component that is NOT wrapped in `<Suspense>`. In Next.js 15 App Router, calling `useSearchParams()` at the top level of a client component forces the entire route to opt into client-side rendering and will throw a build error or deopt the page to fully dynamic rendering. The component is the default export of `app/battle/[id]/replay/page.tsx` — without a Suspense boundary, the page will fail during build (`useSearchParams should be wrapped in a Suspense boundary`) or render a blank/error page in production.

2. **components/replay-controls.tsx:8** — `useState(38)` initialises a hardcoded `progress` value of 38% that never reflects the actual replay position (`elapsed`/`duration` props are completely ignored). The `Play`/`Pause` buttons only mutate a local oscillator (`value >= 96 ? 12 : value + 2`) that jumps around arbitrarily. The `replay-clock` displays `elapsed` but it has no relationship to the `progress` bar, so the visual position and the displayed clock are permanently desynchronised. The component pretends to control replay but does nothing functional — a user clicking Play sees a bar that loops 12%→96% regardless of where they actually are in the replay.

3. **components/event-drawer.tsx:98-106** — The focus-restoration effect captures `document.activeElement` on every render and unconditionally calls `previousFocusRef.current?.focus()` in its cleanup. Because the effect's dependency array is `[open]`, the cleanup fires whenever `open` toggles. Critically, on the **first mount** where `open=false`, the cleanup runs immediately and calls `.focus()` on `<body>` — this runs on every component mount and can steal focus from the user's currently-focused element elsewhere on the page (e.g., if this component re-mounts as a sibling, the page focus jumps to body). The pattern is also racy: the effect sets `previousFocusRef.current` and then synchronously calls `drawerRef.current?.focus()`, but between these two operations a re-render would record the drawer itself as "previous". The `event-drawer.test.tsx` "restores focus" test passes but only exercises the open→close path; the open=false-on-mount or remount path is untested.

4. **components/battle-replay-client.tsx:96-117** — The `ResizeObserver` effect guards against re-observation with `if (resizeObserverRef.current) return`, which **never allows the observer target to be updated** if the scroll container or container ref changes (e.g., navigating between battles with different IDs causes a new DOM but the guard blocks re-attachment). When `battleId` changes the cleanup from the previous observer does run (line 114-117 nullifies the ref), so on a re-mount with a new battleId it works — but if the same `battleId` is used and the container element is swapped (e.g. the page re-renders the container div via a key reset), the ref to the old element persists and the observer stays disconnected from the visible node. The viewport height would then stay frozen at the initial `DEFAULT_VIEWPORT_HEIGHT = 600` regardless of actual screen size.

5. **components/battle-replay-client.tsx:191-200** — `onScroll` updates `scrollTop` via `setScrollTop` on every scroll event without any debounce or `requestAnimationFrame` batching, and updates a useState that causes a full re-render of the entire virtualized timeline. With hundreds of events and rapid scrolling, this floods React's reconciler with renders. The list re-derives `visibleEvents`, `totalHeight`, `startIndex`, `endIndex` on every scroll tick. No `passive` listener flag is set on the DOM event either, so scroll handling cannot be offloaded to the compositor thread and may jank on lower-end devices. Not a crash but a performance cliff at scale.

6. **components/header-actions.tsx:141-157** — The Share dialog renders `event.stopPropagation()` on the panel's `onMouseDown`, but the outer backdrop's `onMouseDown` handler closes the dialog with no early-exit check. When the user clicks inside the dialog panel, `stopPropagation` prevents the backdrop from receiving the `mousedown` — fine. But the **close** `X` button (lines 159-166) also calls `setShareOpen(false)` directly, and the button itself sits **inside** the dialog panel, so its `onClick` fires after `onMouseDown` on the same node — but `event.stopPropagation` on the panel would also stop the click from reaching the backdrop. The pattern is correct but fragile: any event-handler reordering or native dialog focus changes could break it. More critically, the **login dialog** at lines 188-242 uses identical mouseDown pattern and is accessible, but neither dialog traps focus nor restores focus to the triggering element on close — pressing Tab inside the dialog walks focus to elements behind the backdrop, breaking keyboard accessibility.

7. **components/live-battle-client.tsx:76-82** — The SWR fetcher swallows all HTTP errors into `throw new Error(...)` but does NOT check for `redirect`/`forbidden`/`not-found` semantically distinct cases. If the battle API returns 401 or 403, the component renders a generic `statusError.message` like "Status endpoint returned HTTP 401" without differentiating from a transient 500. There is no retry/backoff logic — the SWR `refreshInterval: 2000` will keep polling a 401 endpoint every 2 seconds indefinitely, amplifying load on the auth/backend and hammering the network.

8. **components/arena-cards.tsx:184-214** — `AttackList` uses `getTeam(attack.from)` and `getTeam(attack.to)` and returns `null` silently if either lookup fails (line 190-191). When a new team is added but not registered in `getTeam`, or an attack references a stale team ID, the attack disappears from the UI with no error, no warning, and no fallback row — passengers go missing from the attack matrix. The same pattern exists in `ProposalComparison` (line 220-222) and `DefenseList` (line 260-263). This is silent data loss: the user has no way to know an attack was filtered out.

9. **components/battle-replay-client.tsx:44-48** — `FetchState` state machine has three states: `loading`, `ready`, `error`. There is no `cancelled` state. When the component unmounts mid-fetch (battleId changes, user navigates away), the `cancelled` flag is set in the cleanup, so `setEvents` / `setStatus` are not called — good. But the `useEffect` at line 86 for `?event=` deep-linking depends on `status` and `events`. If the user lands on the page, fetches start, then navigates away before fetch resolves, the effect's cleanup doesn't exist for this effect (no `return` statement), and if `events` later arrives via a React DevTools stale render, `setSelectedEventId` would fire on an unmounted component. React 18+ suppresses this warning but the logic is still a leak.
