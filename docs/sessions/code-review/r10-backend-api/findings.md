# Adversarial Review — Backend API + DB (R10)

Date: 2026-07-10
Reviewer: r10-backend-api

## CRITICAL

1. **`app/api/battles/[id]/cancel/route.ts:2`** — `cancelCurrentBattle` is imported from `@/lib/api/guards` but the cancel handler does not check whether the battle exists or is in a cancellable state. An attacker can POST to `/api/battles/<any-valid-id>/cancel` to call `controller.abort()` on a controller that may belong to a different battle's in-flight operation if ID collision occurs in the `abortControllers` Map (line 293 of guards.ts). Additionally, the `registerAbortController` function in `guards.ts:300-309` does not prevent re-registration: if a battle is restarted while the previous controller is still in-flight, the old controller is aborted but the old in-flight handler may still hold a reference to it. However, the more immediately critical issue is that the cancel endpoint returns `status: "demo_not_cancellable"` for the demo battle but always returns 200 with `{ cancelled: true/false }` regardless of whether the battle actually exists in the DB. A POST to `/api/battles/btl_ABCDEFGH/cancel` for a non-existent battle returns 200 — no 404, no DB check. This allows blind probing of battle IDs and potential denial-of-service via arbitrary abort signals if any controller exists in the registry.

2. **`app/api/battles/[id]/events/route.ts:8-16`** — The `GET /api/battles/[id]/events` handler accepts ANY battle ID string without format validation. It calls `runBattleFromPayload({}, id)` which generates a deterministic bundle for ANY string. There is no `validateBattleId(id)` check, no DB lookup, and no `withRateLimit` wrapper. An attacker can hit this endpoint with arbitrary strings and cause CPU/memory exhaustion by generating full battle bundles for any input. Compare to `/api/battles/[id]/route.ts:18` which correctly validates the ID format. The same issue applies to the stream endpoint at `app/api/battles/[id]/events/stream/route.ts:8-32` — while it validates the ID format, it also lacks rate limiting context appropriate for long-lived SSE connections (the `withRateLimit` wrapper is applied but with default 10 req/min — a streaming connection that holds open consumes its token immediately and then runs unbounded for the duration of the stream).

3. **`lib/db/client.ts:47-83`** — The DB client module caches `cachedDb` at module scope but does not handle the case where `DATABASE_URL` is set during build time or test time and then the deploy environment uses a different URL. The `getDb()` function on line 62 returns `cachedDb` immediately if non-null, meaning a stale connection from a previous environment (e.g. a Neon preview URL cached during the build step) will be used in production. The comment on line 56-58 claims "Reads DATABASE_URL from process.env at call time" but the implementation contradicts this — once `cachedDb` is set on the first call, subsequent calls never re-read the env. This is a connection-pool misconfiguration risk.

4. **`app/api/battles/route.ts:80-94`** — The POST handler inserts a battle row with `id: battleId` where `battleId` is `makeBattleId(idea)` — a deterministic hash of the idea text (format: `btl_<8-char base32>`). However, the `battle.id` column in the schema (`lib/db/schema.ts:147`) is `uuid("id").primaryKey().defaultRandom()` — it expects a UUID. The route handler passes a non-UUID string (e.g. `"btl_QQK7CB1C"`) into the `id` column. This will either: (a) cause a runtime Postgres error when inserting into a UUID-typed column, or (b) if the column type is silently coerced, break the foreign key relationships from `battle_event.battle_id`, `proposal.battle_id`, `score.battle_id`, etc. — all of which are also UUID-typed. The schema mismatch means the entire persistence layer is broken: event store writes, proposal writes, score writes, and passport snapshots will all fail with foreign-key constraint violations because `btl_ABCDEFGH` is not a valid UUID.

5. **`app/api/battles/[id]/status/route.ts:43-49`** — The status route hard-codes `id === "battle-42"` as a demo fallback alongside `"demo"` (line 47). This is a dead-code path that returns a static completed response for an undocumented magic string. More critically, the `STATIC_DEMO_STATE` object (lines 32-41) is typed `as const` with `agentStates` values that include `score: 8.4`, `8.2`, `7.9` — hard-coded score numbers that are returned to the client regardless of actual battle results. Any battle matching `"demo"` or `"battle-42"` gets fabricated scores. Additionally, this route does not check `validateBattleId()` for real battle IDs — it only checks for the two magic strings and otherwise queries the DB with whatever string was passed in the URL. An attacker could pass an arbitrary string as a battle ID and the route will query the DB with it (line 53: `findById(id)`), which is safe against SQL injection (Drizzle parameterizes), but means the route will do unnecessary DB work for every malformed/non-UUID string that doesn't match the demo shortcuts.
