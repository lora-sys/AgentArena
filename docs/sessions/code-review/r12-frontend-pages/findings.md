1. **app/battle/[id]/result/page.tsx:224-236** — Loading and error states both render unconditionally alongside the result content. When `loading` is true, `<ResultSkeleton />` renders. When `error` is set, `<ResultError />` renders. But the `{result && battleId && (...)}` block also renders on the same render pass if state transitions race. More critically, if the initial fetch fails (`error` set, `result` null), the skeleton does not show because `loading` becomes `false` in the catch handler — only the error block shows. However, if `result` was previously loaded and a new fetch error occurs (e.g., battleId param changes), the stale `result` from a prior battleId continues to render while the error for the new one also shows simultaneously. Users see a confusing mix of old champion data + new error message. The conditional rendering should be mutually exclusive: `if (loading) return skeleton; if (error) return error; if (result) return content;` instead of parallel `&&` blocks.
