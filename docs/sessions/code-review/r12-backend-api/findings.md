# R12 Backend API + DB

Date: 2026-07-10

## CRITICAL

1. **app/api/battles/[id]/events/route.ts:8** — `GET /api/battles/[id]/events` handler has **no rate limiting, no input validation, no battle ID format validation, and no authentication**. Any anonymous client can request the full in-memory event log for any battle ID, including resource-intensive `runBattleFromPayload()` calls that execute the entire battle engine synchronously server-side on every request. This is a denial-of-service vector (one HTTP request runs 5 agents through 8 rounds of battle logic) and an information disclosure bug (the response contains all team proposals, attacks, defenses, scores, and passport data).

2. **app/api/battles/[id]/events/route.ts:10** — The handler passes `runBattleFromPayload({}, id)` which passes `idea: undefined` (because the body is empty `{}`). The `makeBattleId()` function in `lib/battle-api.ts:84` falls back to `"agent-arena-demo"` as the seed when `idea` is undefined, meaning **every request with an empty body produces the same deterministic battle ID** — `btl_` + hash of `"agent-arena-demo"`. This means two different battle IDs passed to this endpoint will collide to the same result, and the `events` response will always be the demo fixture regardless of what `id` the client requests.

3. **app/api/battles/[id]/events/stream/route.ts:19-29** — The SSE stream response sends the **entire** event log as one single buffer with no `flush`, no chunking, no streaming. The `Response` body is a fully-buffered string of all events concatenated. For a battle with hundreds of events this blocks the response until every event is serialized. More critically, the SSE format is broken: the body has `\n` as the separator between events but no trailing `\n\n` (each SSE event requires a blank-line terminator per spec). SSE clients that strictly follow the spec (e.g. `EventSource` polyfills, some browsers) may fail to parse events.

4. **app/api/battles/[id]/cancel/route.ts:8-28** — The cancel handler calls `cancelCurrentBattle(id)` which aborts the `AbortController` for that battle ID. However, **the abort controllers are registered in `registerAbortController()`** (called from `start/route.ts:33`), and only the `/api/battles/[id]/start` route registers them. The cancel route has no rate limiting beyond `withRateLimit`, and the `runBattleFromPayload()` call (from `/events` and `/events/stream`) is **synchronous** — by the time a cancel request arrives, the battle has already completed. This means cancel is a no-op for the current synchronous engine and there is no path to actually abort a running AI call. The comment in the code (`route.ts:24`) acknowledges this for demo battles, but the cancel endpoint will **always** return `cancelled: false` in production with the current synchronous engine.

5. **lib/db/repo/battle-repo.ts:38-44** — `findById()` queries `where(eq(battle.id, id))` where `id` is a `string` parameter from the route handler. The `battle.id` column is typed as `uuid` in `lib/db/schema.ts:147`. If a client supplies a string that is not a valid UUID format, the query will **fail at the Postgres level** with an invalid UUID error, causing the `/api/battles/[id]/status` route to hit its DB-unavailable fallback (`route.ts:86-99`) and return a misleading "round: 1, progress: 0, canCancel: true" response instead of a proper 404 or 400. This breaks the battle-status polling for any invalid-but-well-formed battle ID.

6. **lib/battle-api.ts:56-82** — `toBase32Eight()` uses 32-bit FNV-1a hash with `Math.imul` which produces collisions at birthday-boundary speeds. With only 40 bits of entropy (32 + 8 from a second identical hash pass), collisions become probable at ~2^20 ≈ 1M unique ideas. The function is used in `makeBattleId()` which is called from `POST /api/battles` (line 56) where the result is used as a unique battle ID. **A collision means two different users' ideas map to the same `btl_` ID**, causing the unique-constraint check on `battle.idea` (schema.ts:174) to reject one but the client receives the wrong battle ID back. The second pass (line 67-71) is a copy of the first pass, not a different hash — it adds zero additional entropy beyond what the first 32-bit hash already provides (the lower 8 bits of the same hash input are deterministic from the same input).

7. **app/api/battles/[id]/status/route.ts:64-66** — `recentEvents(id, 50)` returns events ordered by `sequence DESC`, so `events[0]` is the **most recent** event. But the code reads `latestEvent?.round` and passes it to `ROUND_ORDER[currentRoundName]`. If the latest event is from `artifact_generation` (round 7), progress reports 7/8 = 0.875. However, if a `battle_failed` or `schema_validation_failed` event is the most recent, its `round` value may be set to the round where the failure occurred (not a round in `ROUND_ORDER`), so `ROUND_ORDER[currentRoundName] ?? 1` falls back to 1 (briefing), making a failed battle appear to be at the very beginning of its lifecycle. The `/status` endpoint for a battle that crashed during round 5 will report `round: 1, progress: 0` — actively misleading the live-page UI.

8. **app/api/battles/[id]/start/route.ts:14-47** — The `runBattleFromPayload` call is **synchronous and CPU-bound** — it executes the entire 5-agent battle through 8 rounds in-memory (including LLM call stubs) inside the request handler. This handler is wrapped with `withGlobalConcurrency` (line 50) which uses `p-queue` with `concurrency: 6`. But `p-queue` runs the handler function directly in the async queue — it does **not** bound total wall-clock time. A single slow battle blocks its concurrency slot until completion. With Node.js' single-threaded event loop, the synchronous `runBattleFromPayload` call (which does not `await` between agent generations) **blocks the entire Node.js process** for the duration of that battle. This means 6 concurrent battles can freeze the server's event loop for the full battle duration, preventing rate-limit processing, SSE heartbeats, and all other requests from advancing.
