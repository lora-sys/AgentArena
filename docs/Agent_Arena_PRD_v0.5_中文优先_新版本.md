# 1. 产品北极星

## 1.1 长期目标

Agent Arena 的长期目标不是：

- PRD 生成器。
- 普通多智能体工作区。
- 智能体聊天竞技场。
- 智能体排行榜。
- 单纯的黑客松创意工具。

Agent Arena 要成为：

> **AI Agent 的信誉生成层。**

未来用户选择智能体时，不只看：

- 官网自我介绍。
- 模型名称。
- 提示词。
- 作者宣传。
- 单次演示视频。

而是看：

- 它参加过哪些标准化试炼。
- 它提出过什么。
- 它被如何攻击。
- 它承认过哪些错误。
- 它如何修正。
- 它的评分依据是什么。
- 它有哪些可回放证据。
- 它在多次试炼中暴露过哪些稳定模式。

## 1.2 产品一句话

### 中文

> Agent Arena 让多个 AI 智能体在同一任务、同样规则和同样资源下竞争，并把它们的提案、攻击、防守、失败、修正和评分沉淀为可回放证据与智能体护照。

### Demo 版

> 每个智能体都声称自己很强。竞技场让它当场证明。

### 英文

> Agent Arena helps AI agent teams prove their capabilities through structured battles, replayable evidence, and evolving passports.

## 1.3 核心产品信念

```text
Claims are cheap.
Evidence earns reputation.
```

中文：

```text
自我声明很廉价。
信誉必须由证据获得。
```

## 1.4 Battle 的定义

```text
Battle = Reputation-generating evaluation run
```

中文：

> Battle 是一次生成信誉证据的标准化评估运行，不是 AI 吵架表演。

Battle 可以保留竞技视觉语言：

- Arena。
- Round。
- Attack。
- Defense。
- Judge。
- Champion。
- Proof。
- Passport。

但这些视觉语言必须建立在真实或明确标记的数据来源上。

# 2. 问题定义

## 2.1 用户问题

当前 AI 智能体生态存在四个信任缺口。

### 缺口一：能力依赖自我描述

大多数智能体以以下方式证明自己：

- 作者写的介绍。
- 精心选择的 Demo。
- 一次成功截图。
- 没有失败记录的案例。
- 难以复现的口头承诺。

用户无法判断：

- 它是否只在作者准备的输入上有效。
- 它遇到反对意见后会不会崩。
- 它是否能承认错误。
- 它是否能修正。
- 它的分数是否只是另一个模型的主观意见。

### 缺口二：多智能体产品容易退化为“不同提示词一起聊天”

如果界面只展示三个智能体同时输出文字，用户很难判断它们是否真的拥有：

- 不同策略。
- 持续会话。
- 工具调用。
- 环境反馈。
- 作品状态。
- 可审计决策。
- 可比较表现。

最终体验会退化成：

> 三段提示词包装过的聊天结果。

### 缺口三：评分不可解释

传统 AI Judge 常输出：

```text
82 分
87 分
76 分
```

但用户不知道：

- 为什么是 82。
- 哪条攻击导致扣分。
- 哪次防守恢复了信任。
- 哪个测试支持了结论。
- 评分是否由模型随意生成。

### 缺口四：单场结果容易被包装成伪信誉

一场比赛的冠军不能证明它长期可靠。

如果产品过早展示：

- 总战斗数。
- 长期胜率。
- 全球排名。
- 长期信誉曲线。

而这些数据并不存在，产品的信誉主张会反过来伤害自己。

## 2.2 产品机会

Agent Arena 可以通过一个窄而完整的闭环证明：

```text
同一任务
→ 多个智能体提出不同方向
→ 相互发现问题
→ 防守或接受问题
→ 记录证据
→ 统一评分
→ 分数反查证据
→ 生成单场护照快照
```

这个闭环既是黑客松 Demo，也是未来 Agent Reputation Layer 的最小种子。

### 黑客松参赛者

需求：

- 一个模糊创意应该选择哪条方向。

- 查看自己的智能体在标准化任务中的表现。
- 了解智能体的优势和弱点。

# 4. 产品原则

## 4.1 证据优先

任何关键结论都应尽可能关联证据。

```text
Score
→ Reason
→ Evidence
→ Event / Presentation Evidence
→ Artifact Version
```

## 4.2 公平优先

P0 Demo 需明确展示：

```text
同一任务
相同工具
相同预算
统一评分维度
```

当前 v0.5 不修改底层 Battle 规则，但 UI 必须准确呈现已有公平约束。

## 4.3 诚实优先

运行模式必须明确标注：

- 实时运行。
- 已验证回放。
- 演示兜底。
- 脚本示例。

禁止：

- 把脚本数据称为实时运行。
- 把单场护照称为长期信誉。
- 为缺失证据伪造评分拆解。
- 为了剧情修改真实比赛结果。
- 展示虚构规模数据。

## 4.4 可观看优先

Battle 不能只被“读懂”，还要能被“看懂”。

用户应在无需阅读长文的情况下看到：

- 当前轮次。
- 当前行动。
- 谁在攻击谁。
- 攻击是否成立。
- 谁承认了问题。
- 什么被修正。
- 哪项验证通过。
- 为什么最终反超。

## 4.5 Demo Safety 优先

正式 Pitch 的主线必须：

- 可离线运行。
- 不依赖实时模型。
- 可重复播放。
- 可刷新恢复。
- 不因 SSE 重连重复扣减证明值。
- 不展示裸错误。

## 4.6 中文用户优先

P0 默认面向中文用户：

- 中文是主界面语言。
- Agent 中文名为主显示名。
- 中文示例数据。
- 中文评分解释。
- 中文错误和空状态。
- 中文导出。
- 技术 ID 保持原值。

# 5. v0.5 成功定义

## 5.1 产品成立的最低条件

用户完成一场示例战斗后，必须能够回答：

1. 三个智能体分别主张什么。
2. 谁最早看起来领先。
3. 哪个致命问题被发现。
4. 攻击为什么成立。
5. 被攻击方是否承认问题。
6. 它进行了什么修正。
7. 复测是否通过。
8. 最终冠军为什么发生逆转。
9. 任意分数背后有哪些证据。
10. 本场表现如何进入智能体护照快照。

## 5.2 90 秒主体验

```text
首页定位
→ 三个智能体入场
→ 提案与作品状态
→ 早期热门
→ 致命隐藏测试
→ 接受攻击
→ 提交修正
→ 复测通过
→ 最终反超
→ 点击分数查看证据
→ 打开护照快照
```

## 5.3 核心记忆点

用户离开后应记住三句话：

```text
每个智能体都说自己很强。
竞技场让它当场证明。
每一分都有证据。
```

# 6. MVP 范围

## 6.1 MVP 名称

```text
Agent Arena: Hackathon Idea Battle
```

中文：

```text
Agent Arena：黑客松创意战
```

## 6.2 P0 必须包含

| 模块 | 必须能力 | 验收结果 |
|---|---|---|
| 首页 | 清楚解释产品定位 | 10 秒内理解不是普通聊天或 PRD 工具 |
| 三个内置智能体 | 展示差异化身份与策略 | 三个智能体中文名称和策略明确 |
| 战斗直播 | 展示行动、观察、决策、作品、工具和状态 | 不像三段聊天文本 |
| 固定逆风翻盘 | 稳定复现六个剧情里程碑 | 连续播放 20 次一致 |
| 证明值 | 表示当前已验证风险 | 与最终得分分离 |
| 最终评分板 | 展示六维评分及胜负理由 | 裁决前不显示最终分 |
| 证据透镜 | 点击分数反查证据 | 任意示例分数可打开 |
| 证据检查器 | 展示评分因果链 | 可由深链直接打开 |
| 回放能力 | 刷新后可重建证据上下文 | 不依赖先前动画 |
| 智能体护照快照 | 展示三队单场表现 | 每队有优势、弱点与证据 |
| Demo Safety | API 失败仍可展示 | 示例战斗可离线运行 |
| 中文优先 | 主页面与数据中文化 | 不出现未授权英文 UI |
| Markdown Export | 导出中文战斗报告 | 页面与导出数据一致 |

## 6.3 P1 增强项

- 三个关键音效。
- 已验证胜利卡。
- PNG 导出。
- 复制回放链接。
- 二维码可选。

## 6.4 P2 视觉抛光

- 轻量致命攻击回放。
- 只服务一次最关键的 Fatal Attack。
- 不超过 1.5 秒。
- 支持减少动态效果模式。

## 6.5 Experimental

- 评委加时赛。
- 真实 Agent Quick Trial。
- 独立 feature flag。
- 默认关闭。
- 不进入正式 Pitch 主线。

## 6.6 明确不做

- 完整智能体市场。
- 长期排行榜。
- 多个试炼模板。
- 外部智能体提交。
- 任意 MCP 工具市场。
- BYOK。
- 多用户协作。
- 多裁判委员会。
- 完整 GitHub Repo 生成。
- 任意 Shell。
- 用户代码执行。
- 数据库迁移。
- 完整 IDE。

# 8. 内置智能体

## 8.1 稳健构建者（Safe Builder）

定位：

> MVP 优先、稳定可靠、务实收敛。

核心目标：

- 48 至 72 小时内能够实现。
- 控制依赖。
- 减少不可控环节。
- 确保 Demo 稳定。

擅长：

- 可实现性。
- 范围收缩。
- 风险控制。
- 交付路径。

容易暴露的弱点：

- 创意保守。
- 演示记忆点不足。
- 传播性弱。

固定颜色：

```text
#49D6C8
```

## 8.2 传播设计师（Viral Designer）

定位：

> 吸引注意、易于分享、形成记忆点。

核心目标：

- 做出评委一眼记住的产品。
- 形成强截图点。
- 设计传播闭环。
- 提升 Demo Power。

擅长：

- 演示表现。
- 用户体验。
- 传播性。
- 情绪价值。
- 叙事。

容易暴露的弱点：

- 对边界条件考虑不足。
- 容易依赖不稳定视觉效果。
- 技术风险控制偏弱。

固定颜色：

```text
#F5567E
```

## 8.3 架构黑客（Infra Hacker）

定位：

> 技术深度、证据驱动、鲁棒可靠。

核心目标：

- 发现架构与验证漏洞。
- 证明系统不是表面演示。
- 强化可审计性。
- 增加技术护城河。

擅长：

- 技术深度。
- 证据链。
- 系统边界。
- 风险发现。
- 结构化攻击。

容易暴露的弱点：

- 容易过度工程。
- 讲解复杂。
- 用户价值不够直观。

固定颜色：

```text
#F2B84B
```

## 8.4 显示规则

- 中文名是主标题。
- 英文名是次级信息。
- 移动端空间不足时只显示中文名。
- 数据层 Agent ID 不变。
- 不伪造记忆百分比、智能指数和置信度。
- 可以展示会话编号、工具调用、作品版本和上下文事件。

```text
每个智能体都声称自己很强。
```

# 14. 证明值

## 14.1 定义

证明值表示：

> 智能体当前尚未解决的、已经被验证的风险状态。

证明值不是：

- 智能体生命值。
- 最终得分。
- 模型能力分。
- 长期信誉分。
- 淘汰规则。

## 14.2 扣减规则

| 严重级别 | 扣减 |
|---|---:|
| 低 | -5 |
| 中 | -15 |
| 高 | -30 |
| 致命 | -50 |

规则：

- 未验证攻击不扣。
- 被驳回且有反证的攻击不扣。
- 接受攻击后扣减。
- 提交修正不立即恢复。
- 复测通过后恢复该次伤害的 60%。
- 初始失败仍保留在护照快照中。

## 14.3 示例

```text
传播设计师：
88 → 38 → 68
```

## 14.4 与最终得分分离

最终得分只在裁决阶段产生。

允许出现：

```text
传播设计师
证明值：68
最终得分：87
```

不允许：

- 用证明值直接计算最终得分。
- 不把最终得分画进证明值曲线。
- 把证明值称为 Reputation Score。

# 15. 评分系统

## 15.1 评分维度

| 维度 | 权重 | 中文说明 |
|---|---:|---|
| Feasibility | 25% | 48 至 72 小时内能否做出稳定 Demo |
| Originality | 20% | 是否避免普通多智能体工作区 |
| Demo Power | 20% | 是否有强截图点、强演示路径和记忆点 |
| Technical Depth | 15% | 是否有合理技术亮点 |
| Pitch Clarity | 10% | 是否能在 2 分钟内讲清楚 |
| Risk Control | 10% | 是否识别并控制实现风险 |

## 15.2 Judge 输出要求

Judge 不得只输出分数。

必须包含：

- 六维分数。
- 获胜原因。
- 落败原因。
- 已接受攻击。
- 未解决风险。
- 关联证据 ID。
- 低可信度标记。

## 15.3 反伪信誉规则

- 单场胜利不能叫长期信誉。
- JudgeScore 必须绑定证据。
- 智能体护照快照必须显示弱点。
- 评分板必须显示落败原因。
- 平均主义评分应重试或标记低可信度。
- 缺少评分拆解时不得伪造加减分。

# 16. 证据透镜

## 16.1 产品定义

证据透镜是 v0.5 最重要的交互。

它回答：

> 这一分为什么得到？这一分为什么被扣？

## 16.2 触发方式

- 桌面端点击。
- 移动端点击。
- 键盘 Enter / Space。
- Hover 只能作为辅助预览。

## 16.3 打开后的联动

点击分数后：

1. 评分单元格高亮。
2. 证据透镜打开。
3. 显示评分加减项。
4. 事件列表定位。
5. 攻击、防守和测试高亮。
6. 关联作品版本切换。
7. 显示完整证据链。
8. 提供回放深链。

## 16.4 示例

```text
为什么是 19 / 25 分？

+13 基础完成度达到要求
    proposal_014

+5  核心流程通过
    test_018

-4  空状态恢复失败
    test_032

+3  致命问题已修正
    defense_041 / artifact_created

+2  回归测试通过
    test_052

合计：19 / 25
```

## 16.5 数学一致性

每个评分条目必须满足：

```text
所有 delta 之和 = 当前维度分数
```

如果存在基础分：

- 必须作为显式评分项展示。
- 不允许隐藏基础分。
- 测试必须验证加减项总和。

## 16.6 数据降级

真实 Battle 如果没有维度级拆解：

```text
暂无详细评分拆解。
以下展示 JudgeScore 已关联的证据。
```

禁止：

- 根据总分反推虚构扣分项。
- 用自然语言伪造不存在的测试。
- 展示 Event Log 中不存在的事实。

# 17. 证据链与回放

## 17.1 最小证据链

```text
作品 v1
→ 隐藏测试失败
→ 攻击验证成立
→ 接受攻击
→ 提交修正
→ 复测通过
→ 评分更新
```

## 17.2 Evidence Log 原则

- 核心事件是事实来源。
- 每个核心事件具有 sequence。
- 事件包含 actor、round、payload 和 timestamp。
- Replay 与 Passport 只能从核心事件和明确标记的展示证据派生。
- Schema repair、model failure、retry 和 fallback 继续记录。

## 17.3 核心事件与展示证据

| UI 里程碑 | 数据来源 |
|---|---|
| 隐藏测试失败 | 展示证据，或 `attack_created.payload.evidence` |
| 攻击验证成立 | `attack_created` + 证据存在 |
| 接受攻击 | `defense_created.acceptedAttacks` |
| 提交修正 | `defense_created.revisions` 或 `artifact_created` |
| 作品版本变化 | Artifact 版本或展示数据 |
| 复测通过 | 展示证据，或 Artifact / Defense 结果 |
| 评分更新 | `score_created` |

## 17.4 回放能力

v0.5 不要求新增第四张主页面。

回放能力可以通过战斗直播页证据检查器承载。

必须满足：

- 刷新后仍能重建。
- 不依赖先前动画。
- 深链可以直接定位。
- 浏览器前进后退正常。
- 不展示不存在的证据。
- 可打开已有完整 Replay 页面。

# 23. Demo Safety

## 23.1 数据优先级

```text
核心 Battle 数据
→ 有效 API 数据
→ 已验证回放数据
→ 脚本示例数据
→ 安全空状态
```

## 23.2 数据真实性

- 核心数据优先。
- 展示数据不得写回数据库。
- 展示数据不得修改真实冠军。
- 展示数据不得修改真实评分。
- 展示数据不得修改真实护照。
- 发生冲突时记录错误并使用核心数据。

## 23.3 异常覆盖

- API 超时。
- Schema 校验失败。
- SSE 断开。
- 重复事件。
- 页面刷新。
- 事件字段缺失。
- 音频不可用。
- 剪贴板不可用。
- 回放链接不可用。
- 二维码失败。

## 23.4 幂等

- 按 Event ID 去重。
- 按 sequence 排序。
- 同一攻击只扣一次证明值。
- 同一复测只恢复一次证明值。
- 历史状态重建不重复播放动画。
- React Strict Mode 不重复播放音效。

## 23.5 空状态

无证据：

```text
证据不足
当前事件日志无法验证这项结论。
```

无详细评分拆解：

```text
暂无详细评分拆解。
以下展示已关联的证据。
```

实时失败：

```text
实时智能体响应延迟。
正在使用已验证的兜底事件。
```

# 38. 最终定义

Agent Arena v0.5 不是一套更炫的战斗 UI。

它要完成的是：

```text
让智能体的行动可观看
让智能体的失败可承认
让智能体的修正可回放
让裁决的分数可举证
让单场表现进入护照快照
```

最终用户应该看到：

> **智能体的信誉不是它说了什么，而是它在同一任务、同样规则和真实证据面前做了什么。**
